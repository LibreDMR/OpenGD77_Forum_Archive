Ok, thanks. I found the source published with the release. It's not very common, but it's fine with me.

A brief update...

I initially focused on the "short boot sequence" reported by me and a few customers. I analyzed the code and saw that it was just the splash screen disappearing very quickly.

I found this in the uiSplashScreen.c file:

if ((ev->events != NO_EVENT) || ((ev->time - initialEventTime) > SILENT_PROMPT_HOLD_DURATION_MILLISECONDS)) {
exitSplashScreen();
}

So, I removed the exitSplashScreen() function completely and displayed the event that was sent on the display:

char c = ev->keys.key
if (ev->events == KEY_EVENT) displayPrintCentered(8, c, FONT_SIZE_3);

I discovered that the system was flooded with a lot of KEY_EVENTs — in my case, the key "0" was being emitted over and over again.
I then tried some trial and error with the keyboardRead function in io/keyboard.c. I changed the speed and doubled the arbitrary delay:

for(volatile int xx = 0; xx < 100; xx++); // arbitrary settling delay

also modified the keyboard matrix and its size to read only a few keys.

Suddenly, the keyboard returned to normal, and I was able to install the unchanged OpenGD77 firmware, which started working again. However, I still receive some unwanted key events. For example, the sweep screen terminates after about 2-5 seconds, or when in VFO mode, if I try to enter a frequency, sometimes a "0" appears unexpectedly.

There might be a problem with my keyboard hardware, but that would be strange since I don't have these issues with the stock firmware, and others are reporting similar issues.

Alternatively, the keyboard initialization or readKeyboard function might not be perfectly compatible with the hardware. I'm still puzzled by how the keyboard can work (at least for me) for 2 days, then completely stop working with many "0" events, and then return to having just some "0" events.

I would either expect to work or not to work, but not to work for some days....

They keyboard GPIO pins are shared with the high speed parallel data bus (FSMC) used by the display.

Possibly the display chip may be driving the GPIO lines, and this would cause these phantom key presses.

You could try changing displayWriteCmd() so that it simply returned and didn't send a command to the display and perhaps the display would then be dormant, albeit you would need see anything on the screen, but this may show whether the display is driving those signals.

Post by G4EML » Tue Dec 03, 2024 11:41 am

I saw the same problem back in the early days of the development.

The settling delay is needed and was added to allow for the capacitance and pull up resistors of the keyboard matrix. It takes a noticeable time for the signals on the selected and unselected rows to stabilise to the correct levels. So reading them too early can result in ghost key presses like you are seeing. There will be differences between individual radios so the current delay might be on the edge of working for your radio. It could be that small changes in temperature or humidity are causing the settling time to vary.

Those delays are quite short so there is probably no harm in doubling them for everybody.

Colin G4EML
