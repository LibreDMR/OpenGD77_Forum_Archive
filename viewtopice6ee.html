Post by G4EML » Tue Sep 03, 2024 3:37 pm

It is unlikely to be a HRC-6000 configuration issue because we are using the same initialisation data as used by the official firmware. (Captured from the original radio) .

As has been mentioned before the HRC-6000 is very poorly documented so most of what we have found has been from observing the original firmware behaviour.

However there may of course be a bug in the code somewhere that has not been found. AMBE packets are very error tolerant so occasional single bit errors will be corrected by the vocoder and not noticed.

I doubt that any of the developers has the time to try to reproduce your findings. It sounds like you are probably the person best equipped to trace further. If you do manage to find the cause it may well help the project overall.

One point mentioned previously by Roger, the USBDebug_printf function was never intended to be used in time critical parts of the code. It can slow things down a lot and may affect normal operation. Whilst it may appear to be working at the moment I would be very cautious when using it.

MD380 uses a different DMR chip. C5000 not the C6000 as used in the UV380. The initialisation of the C5000 is significantly different from the C6000, and its also possible that the C6000 has bugs that the C5000 does not and vice versa.

If you are saying that the data from the C5000 and C6000 are different, this is entirely possible, as they are different chips.


How are you transmitting the silence frames. I presume you have modified the MD380 firmware to send silence frames ?
What is your RF / audio connection between the MD380 and the UV380 ? Have you looked at the received audio signal from the AT1846S Tx/Rx chip, and decoded this using some other means e.g. DSD

Your presumption that there is a in the code presumes that the C6000 is receiving clean audio from the receiver and that your modulation is clean, or have you already verified this ?

The TRx chip used in the UV380 is totally different from the Tx Rx system in the MD380 and the Rx side of the TRx chip is known to be poor quality and also susepetable to interference both in band and out of band, and also is not tollerant of signal overloading.

Even if DSD can demodulate the signal, it does not guarantee that the C6000 can demodulate the signal.

Currently there are many places in the process where your 'silence frame' data could have errors introduced. I don't understand your presumption that this must be a bug in the firmware, when it could be a RF / AF problem

To remove the possiblity that its a RF / AF problem you would need to generate the 4FSK AF encoded signal some other way, and directly inject this into the PCB of the radio, and then adjust the modulation level and attempt to confirm whether this problem is AF/RF


You may be able to use USB Debug print, if you increase the CPU clock frequency. The CPU frequency is controlled by the clock manager code and is changed during Tx and Rx and is always significantly lower than the maximum frequency that the CPU supports.

You should also change the code to prevent the radio entering its Eco / Power saving mode, as this will change the CPU frequency to much lower.
Possibly changing the code so that the firmware leaves the CPU freq at the same it uses for Tx (in DMR mode) may be fast enough to allow USB serial to work in the location you want to view it.

If this is not fast enough you will need to change the clock settings for the entire chip. If you change the CPU clock frequency so that everything runs faster, that you need to ensure that the clock multiplier and divider frequencies provide the correct clock speed for the USB subsystem in the STM32, otherwise USB won't work. Also check the GPIO / SPI / I2C subsystem clock dividers etc to ensure you are not overclocking them if you increase the CPU core frequency.



Generally however, USB serial should not be used in sections of code which have high CPU load or are time critical.
If you have a JLink or STLink there are methods to use the SWD print functionality, however the bootloader disables SWD, so you would need to patch the and reflash the bootloader, or relocate the code to not use the bootloader at all.
